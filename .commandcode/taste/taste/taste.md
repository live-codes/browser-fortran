# Taste
- Prototypes new language/tooling support as a standalone, self-contained proof of concept (e.g. a minimal HTML page) before integrating it into the main project. Confidence: 0.6
- Proactively asks whether existing in-house packages can be reused (e.g. `@live-codes/clang-wasm` for a Fortran pipeline) rather than accepting duplicated toolchain/runtime code. Confidence: 0.6
- Tidies up before reporting a task done: stops background dev servers, closes browser/test sessions, and re-checks the final state (git status, ignored/generated paths, `npm run check`) instead of leaving processes running. Confidence: 0.6
- Maintains a running findings/log document that records what was verified and the evidence for it (verbatim outputs, exact byte sizes, test counts), not just a changelog of edits. Confidence: 0.6
- Documents root causes and deliberately unsupported behaviour explicitly — including why an option/feature was intentionally left out — rather than shipping it undocumented. Confidence: 0.6
- Keeps README/docs in sync with architectural changes (e.g. rewriting them when the code moves into a package) so docs never describe the previous structure. Confidence: 0.6
- When extending an existing package: never change its current public API and avoid growing its bundle size. If a size increase would be significant, ship a separate additional bundle and leave the existing bundle untouched. Confidence: 0.9
- Once a real published release exists, swaps local dev links / `file:` checkouts and `--<pkg>=<dir>` flags for the registry version and deletes the surrounding scaffolding, rather than keeping the workaround around. Confidence: 0.6
- Will not take irreversible, shared-state actions unilaterally (e.g. `npm publish` of a version to a registry): proposes the exact command, explains the one-shot cost (a version can't be reused for 24h after unpublish), and waits for explicit go-ahead even when already authenticated and able to run it. Confidence: 0.6
- Before reporting a blocker or blaming an external service, rules out causes on the local side (registry/proxy config, `private`/`publishConfig` in package.json, stray `.npmrc`, auth identity, `npm pack --dry-run` output) and cross-checks within the same scope (a sibling package returning 200) to isolate whether the problem is theirs or ours. Confidence: 0.5
- Does not trust a version bump blindly: inspects what a newly published package actually ships (tarball contents, exports of each node/browser entry, whether a CDN serves the subpath) before depending on it, and keeps repeated version pins (import map, asset-copy script) in agreement. Treats a "it's published" claim as unverified until the registry agrees (packument resolves, `npm view`/`npm install` succeed, CDN serves it) — a tarball that serves while its packument 404s is treated as an orphaned upload, not a release — and in that case changes nothing and reports the blocker instead of pointing the project at a package that does not resolve. Confidence: 0.7
- Prefers a no-bundler, no-build-step setup for browser demos (native ES modules + an import map, runtime pulled from a CDN) and works to shrink scaffolding — deleting vendor mounts, custom server options and helper code — rather than adding build tooling. Confidence: 0.6
- Serves heavy static assets (multi-MB wasm, data files) straight from the published package's own directory on a CDN (jsDelivr) via the package's built-in option (e.g. `baseUrl`/`clangBaseUrl`) instead of copying, mirroring or vendoring them locally — and pushes back when local copying/mirroring is framed as necessary work, since a package that ships its assets can already be served from the CDN. Confidence: 0.7
- When a page consumes two packages that share a heavy dependency, checks how the CDN's ESM build imports it (externalised URL-like specifier vs. bundled copy) to confirm one shared module instance/runtime, instead of assuming — often with a small disposable probe script that fetches and inspects the built output. Confidence: 0.6
