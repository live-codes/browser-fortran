# Taste
- Prototypes new language/tooling support as a standalone, self-contained proof of concept (e.g. a minimal HTML page) before integrating it into the main project. Confidence: 0.6
- Proactively asks whether existing in-house packages can be reused (e.g. `@live-codes/clang-wasm` for a Fortran pipeline) rather than accepting duplicated toolchain/runtime code. Confidence: 0.6
- Tidies up before reporting a task done: stops background dev servers, closes browser/test sessions, and re-checks the final state (git status, ignored/generated paths, `npm run check`) instead of leaving processes running. Confidence: 0.6
- Maintains a running findings/log document that records what was verified and the evidence for it (verbatim outputs, exact byte sizes, test counts), not just a changelog of edits. Confidence: 0.6
- Documents root causes and deliberately unsupported behaviour explicitly — including why an option/feature was intentionally left out — rather than shipping it undocumented. Confidence: 0.6
- Keeps README/docs in sync with architectural changes (e.g. rewriting them when the code moves into a package) so docs never describe the previous structure. Confidence: 0.6
- When extending an existing package: never change its current public API and avoid growing its bundle size. If a size increase would be significant, ship a separate additional bundle and leave the existing bundle untouched. Confidence: 0.9
- Once a real published release exists, swaps local dev links / `file:` checkouts and `--<pkg>=<dir>` flags for the registry version and deletes the surrounding scaffolding, rather than keeping the workaround around. Confidence: 0.6
- Will not take irreversible, shared-state actions unilaterally (e.g. `npm publish` of a version to a registry): proposes the exact command, explains the one-shot cost (a version can't be reused for 24h after unpublish), and waits for explicit go-ahead even when already authenticated and able to run it. Confidence: 0.6
- Before reporting a blocker or blaming an external service, rules out causes on the local side (registry/proxy config, `private`/`publishConfig` in package.json, stray `.npmrc`, auth identity, `npm pack --dry-run` output) and cross-checks within the same scope (a sibling package returning 200) to isolate whether the problem is theirs or ours. Confidence: 0.5
- Does not trust a version bump blindly: inspects what a newly published package actually ships (tarball contents, exports of each node/browser entry, whether a CDN serves the subpath) before depending on it, and keeps repeated version pins (import map, asset-copy script) in agreement. Treats a "it's published" claim as unverified until the registry agrees (packument resolves, `npm view`/`npm install` succeed, CDN serves it) — a tarball that serves while its packument 404s is treated as an orphaned upload, not a release — and in that case changes nothing and reports the blocker instead of pointing the project at a package that does not resolve. Confidence: 0.7
- Prefers a no-bundler, no-build-step setup for browser demos (native ES modules + an import map, runtime pulled from a CDN) and works to shrink scaffolding — deleting vendor mounts, custom server options and helper code — rather than adding build tooling. Confidence: 0.6
- Serves heavy static assets (multi-MB wasm, data files) straight from the published package's own directory on a CDN (jsDelivr) via the package's built-in option (e.g. `baseUrl`/`clangBaseUrl`) instead of copying, mirroring or vendoring them locally — and pushes back when local copying/mirroring is framed as necessary work, since a package that ships its assets can already be served from the CDN. Confidence: 0.7
- When a page consumes two packages that share a heavy dependency, checks how the CDN's ESM build imports it (externalised URL-like specifier vs. bundled copy) to confirm one shared module instance/runtime, instead of assuming — often with a small disposable probe script that fetches and inspects the built output. Confidence: 0.6
- Ships one canonical language entry per language rather than splitting into dialect- or implementation-specific variants (e.g. rejecting a `fortran77` / `fortran-wasm` split in favour of a single `fortran`, mirroring how the ceiling is shown via the description/snippet rather than a second entry). Explicitly resists entry proliferation for languages few users will need, preferring the cheaper, already-working option over a second integration to own. Confidence: 0.75
- Holds a hard quality bar for user-facing language/feature support: will not ship something that could misbehave ("I want to add Fortran but I do not want the language support to be broken"). An absent feature is acceptable; a shipped one that fails confusingly or silently gives a wrong answer is not, and is reason enough to hold off, or to build/own the missing piece oneself (e.g. producing the compiler artifact in CI) rather than waiting on a third party. Confidence: 0.7
- New packages/artifacts should be shaped like the closest existing sibling in the repo — asked for a Fortran compiler package "similar to" the neighbouring `clang-wasm/packages/clang-wasm`, i.e. same layout and conventions (src with node/browser entries and an exports map, own tests, IIFE build, copy-assets bin, shipped assets with receipts, README/LICENSE/THIRD-PARTY-NOTICES) rather than an ad-hoc structure. Confidence: 0.6
- Treats consequential design trade-offs as a conversation to have before implementing: opens with "let's discuss", asks for a recommendation ("help me choose"), states the constraint that narrows the options, and expects the agent to land on a position and say what would change its mind, rather than deciding unilaterally. Confidence: 0.55
- Grounds architecture and dependency decisions in the upstream project's own source and build files rather than its docs or plausible-sounding assumptions (e.g. confirming the WASM execution path by reading the executor source and upstream test comments, and taking compiler/Emscripten/LLVM versions from the project's own manifest instead of guessing); claims like "this constraint is satisfied" are expected to be backed by having checked the actual build flags/files. Confidence: 0.6
- When a long build or run fails, isolates the failure with the cheapest possible probe before committing to another expensive attempt — running the failing step in isolation, tracing it (`bash -x`, `--progress=plain`, a minimal `docker run` checking tool presence) and checking mundane causes (line endings, trailing-backslash path quoting) — rather than re-running the whole thing and hoping. Confidence: 0.6
- Runs long, unattended builds/runs in the background and reports findings incrementally (interim status plus what each finding means) rather than blocking in silence until the job lands; the user is comfortable letting work continue across several "continue" turns. Confidence: 0.55
- Requires language support to run fully client-side, with no server: "run code in the browser with no servers" — the compiler and the program both execute in the tab, nothing is uploaded, and there is no server-side compilation step. Confidence: 0.75
- Hard constraint against `SharedArrayBuffer` and threaded WebAssembly ("Do not use SharedArrayBuffer"): prefers a single-threaded build by construction so the page needs no cross-origin isolation (COOP/COEP) headers and can be embedded where the top-level headers are not ours to set. Confidence: 0.8
- Prefers containerised (Docker) builds for toolchains the dev machine can't build natively — Windows host, Linux/Emscripten cross-compile — rather than installing the cross toolchain on the host. Confidence: 0.6
- Writes long-running build scripts to be idempotent and resumable: restores mutated files from git before re-appending so retries can't stack duplicate blocks, skips expensive steps whose outputs already exist (e.g. reusing installed `.mod` files instead of rebuilding a native compiler), and tries to reuse already-compiled tree state rather than paying for a clean rebuild. Confidence: 0.6
- Verifies a new implementation against the previous/alternative approach by running the same test corpus through both, so the comparison is direct and the interesting cases (what the old one accepted but got wrong) are surfaced rather than assumed. Confidence: 0.55
